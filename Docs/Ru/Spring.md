# Пружины: модель и план развития

## Назначение

`UMGTransitions` использует пружину для непрерывной анимации одного-четырёх числовых каналов. Это один solver для float, `Vector2D` и цвета: runtime хранит `FVector4f`, поэтому траектория и скорость одинаково определены для всех поддержанных значений.

Документ фиксирует текущий контракт, осознанные ограничения и порядок развития API. Цель — добавить выразительность без превращения простой UI-анимации в физическую систему общего назначения.

## Текущая модель

`FWidgetTransitionSpring` — аналитическое решение затухающего гармонического осциллятора при массе `m = 1`:

```text
x'' + 2 * zeta * omega * x' + omega^2 * x = 0
```

Где `x` — смещение от target, `omega` — собственная частота, `zeta` — коэффициент затухания. Для каждого канала используются общие параметры, но собственные position и velocity.

| Пользовательский параметр | Runtime-смысл |
|---|---|
| `Spring Force` | stiffness; в обычном режиме `omega = sqrt(Force)` |
| `Spring Damping` | UI-нормализованный bounce-контрол `0..1`, отображаемый во внутренний `zeta = lerp(0.15, 1.0, Damping)` |
| `Spring Max Speed` | ограничение длины вектора velocity; `0` означает без ограничения |
| `Fit To Time` | вычисляет frequency из `Time`, чтобы затухание достигло внутреннего порога к дедлайну |
| `EndTolerance` | внутренняя константа `0.001`, относительный порог покоя |

Solver имеет аналитические ветки для underdamped (`zeta < 1`) и critically damped (`zeta = 1`) движения. Public API намеренно не позволяет `zeta > 1`: overdamped-ветка сейчас не нужна и не должна открываться без отдельной формулы.

Завершение требует одновременно малого смещения и малой velocity. После этого value snap-ается в target. Для `Fit To Time` deadline также завершает transition и snap-ает значение в target — это делает внешний контракт duration точным даже на редком неблагоприятном наборе параметров.

### Почему это хороший baseline

- Нет зависимости от численной стабильности Euler-интегратора и накопления ошибки от frame rate.
- Replace и Pipe могут передавать текущую velocity новой пружине, а не создавать визуальный излом.
- Spring state вынесен в плотный массив: linear transition не платит за position и velocity пружины.
- Общий relative tolerance не увеличивает `FWidgetTransition`: основной runtime record остаётся 256 B, spring state — 96 B.

## Границы текущего контракта

1. `Spring Damping` — не буквальный физический damping coefficient и не прямой damping ratio. Это намеренно нормализованный UI-control. Tooltip и имена preset-ов должны описывать визуальный эффект, а не обещать инженерную единицу.
2. `Fit To Time` имеет приоритет над `Spring Force`: frequency вычисляется только из duration, damping и internal tolerance. Force не влияет на этот режим; tooltip явно фиксирует это правило.
3. `Max Speed` ограничивает velocity после аналитического шага. Это сознательный художественный limiter, а не строгое физическое ограничение: после clamp траектория уже не является точным решением уравнения.
4. Нет общих min/max границ. Они семантически различаются между opacity, translation, scale, rotation и материалами; глобальный clamp дал бы неожиданное поведение.

## Приоритеты развития

### P0 — закрепить контракт `Fit To Time` — выполнено

**Проблема.** Пользователь ожидает, что включённый `Fit To Time` означает одинаковую длительность и траекторию независимо от Force. Ранее deadline гарантировался snap-ом, но Force всё ещё влиял на форму и скорость приближения до deadline.

**Решение.** В режиме `Fit To Time` `omega` вычисляется только из `Time`, `zeta` и `EndTolerance`. `Spring Force` не участвует в формуле и остаётся видимым с явным tooltip, что он не влияет на этот режим.

**Критерии готовности.**

- Regression-тест покрывает low/default/high Force и проверяет одинаковый sampled value до дедлайна, а также target в deadline.
- Базовый Fit To Time test проверяет аналитическое затухание и snap в target.

### P1 — `Clamp Overshoot`

**Ценность.** Это самый полезный следующий художественный control для UI. Он предотвращает пересечение target, сохраняя ускоренное приближение. Особенно нужен opacity, progress и scale, где отрицательные значения или выход выше target нежелательны.

**API.** Advanced bool `Clamp Overshoot`, по умолчанию `false`. Он не является глобальным value range.

**Алгоритм.** После шага проверять каждый канал отдельно: если знак смещения до и после шага изменился, установить соответствующий канал в target и обнулить его velocity. Остальные каналы продолжают движение. Это корректно поддерживает смешанные векторы, где один канал пересёк target, а другой ещё нет.

**Стоимость.** Один свободный bit в существующем флаговом `uint16`; размер `FWidgetTransition` не растёт. В tick добавляется несколько сравнений только для spring transition с включённым флагом.

**Тесты.** Underdamped scalar/vector, большой hitch delta, Pipe с перенесённой velocity, completion после clamp.

### P2 — политика Reduce Motion

**Ценность.** Это accessibility-поведение, а не ещё один параметр каждой ноды. Оно должно быть единообразным для всего UI.

**Решение.** Добавить настройку плагина с режимами `System`, `Always Reduce`, `Never Reduce`. При reduction spring либо сразу переходит в target, либо заменяется коротким non-bouncy linear transition — выбор фиксируется одной политикой проекта.

**Стоимость.** Не добавлять flag в `FWidgetTransition`; решение принимается при добавлении transition. Нужны editor/runtime тесты настройки и сохранения lifecycle callbacks.

### P3 — presets, а не новые физические поля

**Ценность.** Большинству Blueprint-пользователей нужны повторяемые ощущения: `Gentle`, `Snappy`, `Bouncy`, `Critical`, а не поиск правильной комбинации чисел.

**Решение.** Набор именованных preset-ов задаёт Force и UI Damping. Он может быть настройкой/таблицей либо чистой функцией, возвращающей transition. Custom остаётся без ограничений.

**Правило хранения.** В transition сохраняются конечные Force/Damping, не идентификатор preset-а. Это сохраняет независимость уже созданного transition от последующих правок preset-ов.

**Тесты.** Значения preset-ов, monotonic critical profile, наличие overshoot у Bouncy, воспроизводимость снапшотов.

### P4 — внешний Initial Velocity для интерактивного UI

**Ценность.** Для release после drag/scroll пружина должна продолжать реальную скорость жеста. Внутренняя передача velocity между Replace/Pipe уже реализована; этот шаг открывает вход извне.

**API.** `Initial Velocity` того же семантического типа, что и Transition Value. Для жестов скорость должна быть нормализована относительно расстояния до target; при нулевой дистанции соответствующий канал равен нулю.

**Хранение.** Не добавлять `FWidgetTransitionValue` в каждый transition: это увеличит hot record на 32 B. Использовать spring-only sidecar/configuration, создаваемый только при явном external velocity, либо передавать значение непосредственно в `Add`-вариант для интерактивного использования.

**Тесты.** Направление velocity, zero-distance, Replace/Pipe continuity, max-speed interaction.

### P5 — binding-specific bounds

**Ценность.** Для некоторых свойств естественны ограничения: opacity `[0, 1]`, progress `[0, 1]`, некоторые scale — неотрицательны.

**Решение.** Это не базовая настройка spring. Ограничения должны задаваться adapter-ом binding либо отдельной opt-in функцией transition, потому что корректный диапазон зависит от конкретного свойства.

**Условие начала.** Добавлять только после реального кейса, который нельзя выразить `Clamp Overshoot` или пользовательским target.

## Сознательно отложено

### Mass

Полный физический API `mass + stiffness + damping coefficient` корректен, но для UI создаёт три взаимозависимых параметра. При нашей фиксированной массе результат уже контролируется Force и Damping. Mass стоит добавить только при внешней интеграции, где нужно переносить реальные физические параметры без преобразования.

### Overdamped режим (`zeta > 1`)

Полезен редко: визуально это просто медленное монотонное приближение. Пока API нормализует Damping до critical damping, пользователь не может случайно получить этот режим. Открывать его можно только вместе с аналитической overdamped-веткой и тестами на непрерывность возле `zeta = 1`.

### Независимые параметры по каналам

Разные пружины для X/Y/R/G/B способны дать необычные эффекты, но ломают цельность движения и существенно усложняют данные. Для обычных UMG transition это не оправдано.

## Рекомендированный порядок реализации

1. Добавить `Clamp Overshoot`.
2. Ввести проектную policy Reduce Motion.
3. Добавить presets.
4. Реализовать external Initial Velocity только при появлении drag/interactive use case.
5. Рассматривать bounds, mass и overdamped только по подтверждённым продуктовым сценариям.

Такой порядок сохраняет компактность hot path, улучшает предсказуемость существующего API и добавляет видимую ценность раньше, чем расширяет физическую поверхность системы.
