# Кеш кубического easing — 2026-09-10

> Архив эксперимента. Актуальный runtime использует 12-шаговый binary search без кэша и `SolveCubic`; см. [Расчёт cubic Bézier](../CubicBezier.md).

## Итог экспериментов

Во время эксперимента был возвращён `SolveCubic` с проверкой корня и fallback. Прямой вариант `BezierToPower → SolveCubic → BezierInterp` без дополнительных проверок отклонён: он НЕ прошёл regression (18/19). На допустимой кривой P1=(0,0), P2=(1/3,0) значение при Progress=.25 равно 0 вместо .125; на матрице из 784 кривых встречается бесконечная ошибка. Лог: `/tmp/UMGTransitionsSolveCubicDirect.log`.

Прямой вариант на 500 транзишенах: 23.632 мкс/кадр без биндинга, 40.334 с биндингом; на 100: 4.689 / 7.565. Выигрыша относительно SolveCubic с fallback в этих одиночных прогонах нет. Стандартный solver подменяет нулевой кубический коэффициент очень малым числом, что не равнозначно корректному решению квадратного уравнения.

## Этап LUT

Следующее описание относится только к экспериментальному варианту с таблицей. Его код и поле shared pointer удалены из текущего runtime.

В варианте LUT при активации easing-транзишена StartTransition строил 129 точек Bézier с равномерным шагом по параметру t. Координаты X образуют упорядоченную таблицу времени. В тике выполняются семь шагов поиска соседей и линейная интерполяция Y. Полином и обратная задача X(t) в тике больше не вычисляются.

Кеш строится также при активации элемента Pipe, сохраняется при repeat/yoyo и пересоздаётся при новом StartTransition. Определение кривой остаётся двумя точками. Таблица принадлежит runtime-транзишену через shared pointer: копии разделяют неизменяемый кеш, данные не сериализуются. Payload таблицы — 1032 байта плюс служебные данные shared allocation; поле shared pointer занимает 16 байт на arm64. Для 500 easing-транзишенов таблицы занимают 516000 байт без allocator overhead. Linear и spring таблиц не выделяют.

В экспериментальных Evaluate и кеше были точные значения 0/1 на концах. При восстановлении исходного binary 12 эти early return также сняты.

## Проверки

EasingCache сравнивает 400 комбинаций ручек (X: 0, .25, .5, .75, 1; Y: -2, 0, 1, 3) по 999 значениям времени с независимым поиском из 40 итераций. Максимальная наблюдаемая абсолютная ошибка нормализованного Y — 0.003147. Это измерение на выборке, а не доказанная граница для всех кривых. Ошибка масштабируется на разницу From/To. Тест также проверяет создание кеша через StartTransition и достижение точного конечного значения.

## Эксперимент SolveCubic

В том же окружении runtime переключён на SolveCubic с проверкой корня и fallback, таблицы не создаются. Все 19 тестов (Runtime, Metadata, ModeMatrix) прошли. На 784 кривых × 999 отсчётов максимальная ошибка против 40 итераций независимого поиска составила 0.000009429. Лог: `/tmp/UMGTransitionsSolveCubic.log`.

| Easing-транзишены | Биндинг | Исходный поиск, мкс/кадр | LUT, мкс/кадр | SolveCubic + fallback, мкс/кадр |
| --- | --- | ---: | ---: | ---: |
| 100 | Нет | 6.396 | 2.943 | 4.492 |
| 100 | Есть | 9.113 | 6.756 | 7.274 |
| 500 | Нет | 29.919 | 13.990 | 22.819 |
| 500 | Есть | 47.722 | 34.174 | 37.736 |

SolveCubic быстрее исходного поиска, но медленнее LUT на стандартной кривой benchmark. Его преимущество — отсутствие таблиц и их аллокаций при активации. Стоимость зависит от числа корней и попадания в fallback; эти tick-замеры относятся к P1=(.25,.1), P2=(.25,1), а не ко всем допустимым кривым. На этом этапе SolveCubic временно оставался для оценки. Итог: восстановлен binary 12, SolveCubic и LUT-код удалены; shared pointer в текущей структуре отсутствует.
