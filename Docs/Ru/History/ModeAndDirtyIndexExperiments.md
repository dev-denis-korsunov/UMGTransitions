# Эксперименты: индексы режимов и dirty widget

Этот документ описывает два изолированных perf-теста. Они не меняют публичный API и не считаются доказательством, что соответствующая архитектура должна попасть в runtime: сначала измеряется цена дополнительной индирекции.

## Индексы режимов

При добавлении transition его режим неизменяем: Linear, cubic Bezier easing или Spring. Поэтому можно один раз добавить индекс transition в один из трёх плотных массивов:

```text
LinearTransitionIndices
EasingTransitionIndices
SpringTransitionIndices
```

В tick каждый массив обрабатывается отдельным проходом. Потенциальная выгода — отсутствие branch по режиму внутри цикла и возможность специализировать путь. Цена — чтение индекса и непрямой доступ к `Transitions[Index]`.

`Experiments.ModeIndices` сравнивает эти два маршрута на одинаковых 500 transition, поровну распределённых между тремя режимами. Он измеряет только выбор режима и вычисление value; tick spring, widget binding, callbacks и удаление исключены, чтобы увидеть именно цену индирекции. Если grouped traversal не лучше последовательного обхода, добавлять три runtime-массива не имеет смысла.

## Dirty widget indices

Несколько transition могут менять разные свойства одного widget за кадр. Постоянные группы вида `Widget → TransitionIndices` позволяют обрабатывать их рядом:

```text
DirtyWidgetGroups
  Widget A → [transition 2, 7, 14]
  Widget B → [transition 1, 8]
```

Исторический `Experiments.DirtyWidgetIndices` сравнивал прямой обход transition и обход заранее построенных групп для 500 `RenderOpacity` writes по 50 widget. Группы строились вне измерения: тест отвечал на вопрос о стоимости hot traversal, а не о цене `TMap` grouping. После решения не внедрять группы в runtime исходник теста удалён.

Важно: группировка **сама по себе не уменьшает число setter вызовов**. Публичные `UWidget::Set...` самостоятельно выполняют нужную invalidation, и обход этого механизма небезопасен. Поэтому результат будет полезен только как locality-замер. Реальный выигрыш dirty widget возможен, если движок даёт безопасный batched write/invalidation API; до этого момента эта схема не должна менять порядок применения свойств или пропускать setter.

## Результаты

Прогон: UE 5.7 / Mac arm64 Development, 24 августа 2026, 500 transition, 300 кадров.

| Сценарий | Прямой обход, μs/frame | Индексный обход, μs/frame | Разница |
| --- | ---: | ---: | ---: |
| Режимы Linear/Easing/Spring, общий evaluator | 1.438 | 1.368 | −4.9%, предварительно |
| Режимы Linear/Easing/Spring, специализированные пути, среднее 3 прогонов | 1.537 | 1.268 | −17.5% |
| 500 `RenderOpacity` writes / 50 widget | 1.707 | 1.656 | −3.0% |

Первый прогон вызывал один и тот же общий evaluator и в индексных проходах, поэтому проверки режима в нём ещё оставались. После замены на три специализированных пути получены три независимых прогона:

| Прогон | Mixed pass, μs/frame | Specialized index passes, μs/frame |
| --- | ---: | ---: |
| 1 | 1.571 | 1.291 |
| 2 | 1.520 | 1.256 |
| 3 | 1.520 | 1.256 |
| Среднее | 1.537 | 1.268 |

Выигрыш `0.269 μs/frame` (17.5%) заметно больше разброса между прогонами. Это доказывает пользу specialization в данном изолированном compute path, но ещё не включает настоящий spring tick, widget binding, callbacks и удаление. Dirty widget groups подтверждают небольшую locality-выгоду, однако не дают права объединять или пропускать публичные widget setter: отдельной оптимизации invalidation здесь нет.

## Решение

- **Mode indices:** specialization подтверждена в compute benchmark. Следующий этап — сравнить варианты в реальном runtime loop с tick spring, binding, callbacks и удалением. Если существенная часть выигрыша сохранится, в subsystem добавить три плотных массива индексов без миграций после `Add`: режим transition неизменяем. Для `RemoveAtSwap` понадобится обновлять только индекс перемещённого transition в соответствующем массиве.
- **Dirty widget groups:** пока не добавлять в runtime. Сначала нужен безопасный UE API для batched write/invalidation либо более крупный выигрыш в интеграционном тесте. Иначе новый bookkeeping не окупает около 3% в изолированном setter loop.
