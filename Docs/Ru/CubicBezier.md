## Кривая

Runtime использует cubic Bézier с точками:

```text
P0 = (0, 0)
P1 = FirstControlPoint
P2 = SecondControlPoint
P3 = (1, 1)
```

Параметр `t` проходит от `0` до `1` и определяет положение на curve. Геометрически вычисляются две функции: `X(t)` и `Y(t)`.

## Почему `t` не равно времени

В transition входной `Progress` — это нормализованное время, то есть координата `X`, а нужно получить выходное значение `Y`.

```text
Progress = X
найти t, для которого X(t) = Progress
EasedProgress = Y(t)
```

`t` совпадает с `X` для всех значений только при `P1.X = 1/3` и `P2.X = 2/3`. При этом `P1.Y` и `P2.Y` могут быть любыми: easing по Y всё равно может быть нелинейным.

Даже диагональная геометрическая кривая `Y(X) = X` не обязана проходиться равномерно по `t`; она лишь возвращает тот же итоговый прогресс.

## Расчёт значения

Runtime clamp-ает progress в диапазон `[0, 1]`, затем 12 раз делит интервал `t ∈ [0, 1]` пополам. На каждом шаге сравнивается `X(t)` с входным Progress; остаётся половина, содержащая искомый `t`. После последнего шага `Y(t)` становится eased progress.

Это намеренно простой и предсказуемый метод: control X ограничены диапазоном `[0, 1]`, поэтому временная ось монотонна, а бинарный поиск устойчив для обычных и вырожденных cubic/quadratic cases. Он не использует `SolveCubic`, кэш или аллокации.

## Ограничения и точность

| Координата | Допустимый диапазон | Причина |
| --- | --- | --- |
| `P1.X`, `P2.X` | `0..1` | Сохраняет корректную временную ось и единственное решение `X(t)`. |
| `P1.Y`, `P2.Y` | `-2..3` | Разрешает контролируемый overshoot, не открывая бесконечный диапазон editor. |

Точность solver должна быть достаточной для UI, а не для CAD-геометрии. Изменение числа итераций, метода поиска или кэширования требует сравнения с independent reference и performance-прогона.

## Производительность и тестирование

### Текущее покрытие

| Runtime.CubicEasing | Проверяемый результат |
| --- | --- |
| Контрольные точки (-1,-5), (2,5) | Clamp в (0,-2), (1,3) |
| Evaluate(0), Evaluate(1) | Приближение endpoints с допуском теста |
| Ручки (0.25,1), (0.75,1) | Evaluate(0.5) > 0.7 |

Тест не проверяет linear fallback, полный диапазон кривых или точность относительно reference. Текущие 12 шагов оставляют интервал t шириной 1/4096; возврат середины даёт ошибку t не более 1/8192 в точной арифметике. Это не такая же граница ошибки Y: её увеличивает наклон Y(t). Отдельных точных early return для endpoints в восстановленном варианте нет.

### Точность, память и решение

| Вариант | Проверка точности | Дополнительная память | Статус |
| --- | --- | --- | --- |
| Binary 12 | Текущее ограниченное покрытие выше | Нет таблицы | Оставлен за простоту |
| LUT, 129 точек по t | 400 кривых ×999 samples; max ошибка Y 0.003147 | 1032 B payload/curve + allocation; shared pointer 16 B в эксперименте | Отклонён после экспериментов |
| SolveCubic + fallback 24 | 784×999; max ошибка 0.000009429 | Нет таблицы | Эксперимент снят |
| Прямой SolveCubic | 18/19 тестов; на матрице бесконечная ошибка | Нет таблицы | Отклонён: вырожденные полиномы |

LUT для 500 кривых требовал 516 000 B payload сверх allocator overhead. Построение таблицы исключено из tick-замера; цена её активации не измерена этой таблицей.

**Вывод:** LUT дал меньшую tick-стоимость на выбранной кривой, но добавил память и погрешность. Текущий выбор binary не является победителем скорости. Возвращаться к оптимизации следует при подтверждённом easing-бюджете; сравнивать надо также activation, память и representative curves. Исходные этапы и логи: [эксперименты Bézier](History/BezierCache.md#производительность).
